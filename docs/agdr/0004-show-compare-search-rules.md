# Правила show, compare, search, плюсов и минусов, перевода и целостности

## Context
ТЗ v0.6 (FR-4, FR-5, FR-8) задаёт, что команды должны делать, но не фиксирует: как находить модель по введённому имени, по какому эталону считать плюсы и минусы, формат `descriptions_ru.json` и признак устаревшего перевода, что значит «устаревшая» запись `name_map.json`. Шаг 6 (перевод агентом) зависит от формата файла переводов.

## Options considered
| Вопрос | Варианты |
|---|---|
| Поиск модели | (1) точное совпадение id / id варианта / id без разработчика / имени, затем все слова запроса как подстроки; при нескольких совпадениях — ошибка со списком; (2) брать первое совпадение; (3) только точный id |
| Эталон для плюсов и минусов | (1) распределение среди чат-семейств без алиасов (как в рекомендациях), перцентили из конфигурации, внутри источника и метрики; (2) только модели того же разработчика; (3) абсолютные пороги в config |
| Формат перевода | (1) `{schema_version, descriptions: {family_id: {text, source_hash, translated_at}}}`, `source_hash` — sha256 описания с нормализованными пробелами; (2) хеш сырой строки; (3) сравнение текста оригинала, хранимого в файле |
| Устаревшая запись | (1) id нет в каталоге → предупреждение в заголовке каждой команды, файл не меняется; (2) удалять при запуске; (3) молчать |
| Битый необязательный файл | (1) предупреждение и игнорирование; (2) ошибка |

## Decision
- Поиск: вариант 1. Неоднозначный запрос не угадывается; `show` и `compare` принимают алиасы с `~` и без него. `search` показывает и алиасы, и не-чат (AC-20). Несколько слов в запросе — подстроки в любом порядке.
- Эталон плюсов и минусов: вариант 1. Правила и пороги — раздел `pros_cons` в `config.json`: верхние 25% (`top_percentile` 75) → плюс; ниже медианы → минус; оба правила по каждой из четырёх метрик, только если в источнике метрики не меньше `min_pool_size` (10) моделей; image во входе → плюс, иначе «нет vision»; контекст ≥ 1M → плюс, < 32K → минус; output выше 75-го перцентиля каталога → «дорогой output», не выше 25-го → «дешёвый output». Отсутствие оценок — минус «нет оценок ни в одном бенчмарке», не нулевая оценка. Правило «ниже медианы по скорости» из примера ТЗ не реализовано: скорость в снапшоте оценок не хранится.
- Перевод: вариант 1. Хеш считается функцией `description_hash` в `query.py`; агент на шаге 6 обязан использовать её же. Перевод показывается с пометкой «машинный перевод» и датой; невалидная запись, отсутствие записи и несовпадение хеша дают оригинал (в последнем случае пометка «перевод устарел» и предупреждение). В списках описание обрезается по `description_max_chars`, в карточке `show` — нет.
- Целостность: вариант 1. Проверяются id из `name_map.json` (совпадения и кандидаты) и `descriptions_ru.json`; предупреждения идут сразу после заголовка свежести в каждой команде. Файлы не изменяются.
- Битый или неподдерживаемой версии необязательный файл — предупреждение и игнорирование (вариант 1): справка не должна падать из-за вспомогательного файла.
- Значения в `compare` и `show` берутся как есть у семейства, включая алиасы и не-чат; пометка «источники смешаны» ставится, если в таблице есть оба источника.

## Consequences
- `name_map.json` не коммитится (лицензия AA), поэтому проверка целостности для него работает на машине пользователя, а не в репозитории.
- Формат `descriptions_ru.json` становится контрактом для шага 6; смена способа хеширования требует `schema_version` 2.
- Плюсы и минусы воспроизводимы, потому что считаются по снапшотам и конфигурации; пересмотр порогов — правка конфигурации.
- Пороги плюсов и минусов черновые; проверяются на приёмке (шаг 7).
