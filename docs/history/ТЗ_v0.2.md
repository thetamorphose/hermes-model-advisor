# ТЗ — «Советник по моделям Nous» (портативный скилл)

Версия 0.2 · Дата: 2026-10-17 · Статус: черновик на согласование

---

## 1. Цель и назначение

Помочь пользователю подписки Nous Portal быстро отвечать на вопросы вида:

- «Какие модели сейчас актуальны и сколько они стоят?»
- «В чём особенности, сильные и слабые стороны модели X?»
- «Какая модель лучше всего подойдёт под мою задачу по соотношению цена/качество?»
- «Сравни X и Y — что выбрать?»

Инструмент реализуется как **портативный скилл** — набор файлов, который можно запускать независимо от движка/агента (Hermes, Claude Code, обычный Python), не завязанный на конкретный агентский runtime.

---

## 2. Термины

| Термин | Значение |
|---|---|
| **Каталог** | Список моделей, доступных через Nous Portal (≈426 шт.), с метаданными и ценами |
| **Снапшот** | Локальная копия каталога (`models.json`), сгенерированная скриптом fetch |
| **Курируемый слой** | Человеко/агентно-поддерживаемые заметки: плюсы, минусы, нюансы, оценки качества |
| **Spotlight** | Курируемый список «актуальных/нашумевших» моделей для обзора рынка |
| **Категория задачи** | Тип работы, под который подбирается модель (кодинг, бизнес-ТЗ и т.д.) |
| **Value-оценка** | Итоговая метрика «цена/качество» для рекомендации |

---

## 3. Пользовательские сценарии

1. **Обзор рынка.** «Покажи актуальные модели» → список «нашумевших»/популярных моделей — **не только флагманы, но и нишевые**, о которых любопытно узнать, с ценами и краткой аннотацией «почему примечательна».
2. **Справка по модели.** «Что такое DeepSeek V4 Pro? Какие у него минусы?» → карточка: описание, сильные/слабые стороны, нюансы, цена.
3. **Подбор под задачу.** «Мне нужно писать код» / «составить бизнес-ТЗ» → топ-N моделей с наилучшим соотношением цена/качество (бюджет пользователь не задаёт — всегда оптимизируется value).
4. **Сравнение.** «Сравни Claude Sonnet 5.5 и DeepSeek V4 Pro» → таблица: цена, контекст, модальности, оценки по категориям, вердикт.
5. **Обновление.** «Обнови каталог» → пересоздание снапшота с живыми данными.

## 4. Функциональные требования

### FR-1. Получение и хранение каталога
- Скрипт тянет список моделей из `https://inference-api.nousresearch.com/v1/models` (Bearer-токен).
- Нормализует цены в **$/1M токенов** (в API они приходят в долларах за 1 токен — умножать на 1e6).
- Сохраняет снапшот `models.json` со схемой из §6.
- Повторный запуск идемпотентен (перезаписывает файл, фиксирует `fetched_at`).

### FR-2. Справочник по модели (курируемый слой)
- Для каждой модели из курируемого списка хранится: краткое резюме, сильные стороны, слабые стороны, нюансы/ограничения, «лучше всего для» (теги задач).
- Отдельный курируемый список **`spotlight`** — «актуальные/нашумевшие» модели для обзора рынка: не только флагманы, но и нишевые/любопытные, с пояснением «почему примечательна».
- Покрытие v1: **40–60 ключевых моделей** (флагманы + популярные + spotlight), остальные 400+ — только метаданные из каталога.

### FR-3. Подбор под задачу (цена/качество)
- Список категорий задач с весами (см. §7) — расширенный: кодинг, бизнес-ТЗ, техническое ТЗ, письмо, перевод, аналитика, vision, креатив и др.
- Для каждой категории у модели есть **оценка качества** (0–100, курируемая).
- Пользователь **не задаёт бюджет** — всегда оптимизируется value (качество на цену).
- Формула value: `quality × веса_категории / смешанная_цена`, плюс порог минимального качества.
- Вывод: топ-N моделей в категории с обоснованием; опциональная группировка по «оптимально» / «бюджетно» / «премиум» (без ввода бюджета пользователем).

### FR-4. Сравнение моделей
- Принимает 2+ идентификаторов моделей, выдаёт таблицу:
  цена (in/out), контекст, модальности, оценки по всем категориям, вердикт-строка.
- Поддерживает поиск по алиасам (не только точный id).

### FR-5. Обновление и поддержание актуальности
- Обновление каталога — одна команда (fetch).
- Обновление курируемого слоя — редактирование `curated.json` / `curated/*.md` по процедуре из SKILL.md.
- При несовпадении id между снапшотом и курируемым слоем — предупреждение о «протухших» записях.

### FR-6. Индикация свежести снапшота
- **Каждый вывод** (list/show/search/recommend/compare) начинается с заголовка: дата создания снапшота (`fetched_at`) + возраст («создан сегодня / 3 дня назад»).
- При возрасте старше порога (по умолчанию 7 дней) — подсказка «снапшот устарел, обновите: `python3 scripts/fetch_models.py`».

## 5. Нефункциональные требования

### NFR-1. Портативность (ключевое требование)
- Скилл — самодостаточная директория: `SKILL.md` + `scripts/` + `data/`.
- Скрипты на **чистом Python 3.10+ (stdlib only)**: `urllib`, `json`, `argparse`, `pathlib`. Без `requests`, без зависимости от пакета hermes.
- Запуск: `python3 scripts/query.py ...` — одинаково работает из любого агента или вручную из терминала.
- **Получение токена** по приоритету:
  1. аргумент `--token`
  2. переменная окружения `NOUS_API_TOKEN`
  3. автопоиск в `auth.json` (проверяются `~/.hermes/auth.json`, `$HERMES_HOME/auth.json`, `%LOCALAPPDATA%\hermes\auth.json` на Windows)
- **Offline-режим:** если токена/сети нет, «рекомендовать» и «сравнить» работают на вшитом снапшоте + курируемом слое (без живых цен).

### NFR-2. Актуальность
- Снапшот обновляется по запросу (`fetch`); у него всегда есть метка времени.
- Курируемый слой версионируется; устаревшие модели помечаются, а не удаляются молча.

### NFR-3. Расширяемость
- Добавление новой модели = запись в `curated.json` без изменения кода.
- Добавление новой категории задачи = строка в списке категорий + оценки.
- Формат данных задокументирован (JSON Schema или эквивалент) для внешних инструментов.

### NFR-4. Воспроизводимость
- Вывод детерминирован: одинаковый снапшот + курируемый слой → одинаковый результат.
- Все вычисления цен и value — в коде, не «на глаз».

## 6. Архитектура и структура скилла

```
hermes-model-advisor/
├── SKILL.md                  # входная точка для агента: триггеры, как запускать, как поддерживать
├── scripts/
│   ├── fetch_models.py       # FR-1: тянет /v1/models → data/models.json
│   └── query.py              # FR-2..4, FR-6: list / show / search / recommend / compare
├── data/
│   ├── models.json           # снапшот каталога (генерируется, в git не коммитить как источник истины)
│   └── curated.json          # курируемый слой (FR-2, FR-3) — источник истины по качеству
└── references/
    └── maintenance.md        # как обновлять оценки, откуда брать данные, чек-лист ревизии
```

## 7. Модель данных «цена/качество»

### Категории и типовое соотношение input:output
Для оценки реальной цены задачи нужно учитывать, сколько токенов уходит на вход и выход:

| Категория | Что покрывает | Типовое in:out | Вес |
|---|---|---|---|
| coding | Программирование, код-ревью, отладка | 3:1 | 1.0 |
| reasoning | Математика, логика, сложные рассуждения | 2:1 | 1.0 |
| agentic | Агентные задачи: инструменты, длинный контекст | 5:1 | 1.2 |
| business_spec | Составление бизнес-ТЗ, бизнес-документация | 2:1 | 1.0 |
| tech_spec | Составление технического ТЗ, спецификаций | 3:1 | 1.0 |
| writing | Письмо, редактура, структура текста | 1:1 | 0.7 |
| translation | Перевод | 1:1 | 0.6 |
| data_analysis | Анализ данных, длинные документы, извлечение | 6:1 | 1.0 |
| vision | Визуальные/мультимодальные задачи | 4:1 | 0.8 |
| creative | Креатив, генерация идей, сценарии | 1:2 | 0.7 |
| budget | Массовые/дешёвые задачи (bulk) | 5:1 | 1.0 |

### Формулы
```
смешанная_цена(категория) = prompt×ratio_in + completion×ratio_out
value = quality × вес_категории / смешанная_цена
```
Порог: модель попадает в рекомендацию только при `quality ≥ 70` в категории. Дополнительно выводятся отдельные списки «бюджетный» (низкая цена) и «премиум» (максимальное качество) — без ввода бюджета пользователем.

### Источники оценок качества (нужно решение — см. §10)
- **Курируемые оценки** (рекомендуется для v1): ручные 0–100 по категориям, опираются на бенчмарки (LiveCodeBench, GPQA, AIME, MMLU) и консенсус сообщества.
- **Авто-импорт лидербордов** (опционально, позже): LMArena / Artificial Analysis, но они отстают от каталога и не покрывают все модели.

## 9. Критерии приёмки

- [ ] `python3 scripts/query.py compare deepseek/deepseek-v4-pro anthropic/claude-sonnet-5.5` → корректная таблица цены+качества.
- [ ] `python3 scripts/query.py recommend --task coding` → топ-N с обоснованием (без бюджета), модели реально пригодны.
- [ ] `python3 scripts/query.py list` → список spotlight-моделей с аннотациями «почему примечательна».
- [ ] `python3 scripts/fetch_models.py` на чистой машине (Python 3.10+, токен через `NOUS_API_TOKEN`) → валидный снапшот 400+ моделей.
- [ ] Без токена/сети `query.py` работает на вшитом снапшоте (offline).
- [ ] Каждый вывод начинается с даты и возраста снапшота; при возрасте > 7 дней — подсказка обновить.
- [ ] Цены в выводе совпадают с ценами на portal.nousresearch.com (выборочная сверка).
- [ ] Курируемый слой не содержит «протухших» id (проверка на запуске).

## 10. Открытые вопросы (решения нужны до реализации)

1. **Источник оценок качества.** Курируемые вручную (v1) или сразу авто-импорт лидербордов? → *Рекомендую: курируемые + опциональный импорт позже.*
2. **Размер курируемого покрытия.** 40–60 моделей достаточно для v1, или нужно шире?
3. **Язык заметок.** Курируемые резюме/плюсы/минусы — на русском? → *Рекомендую: русский.*
4. **Набор категорий задач.** Расширен (кодинг, бизнес-ТЗ, тех-ТЗ, письмо, перевод, аналитика, vision, креатив, бюджет, рассуждения, агентные) — подтвердить финальный список и веса из §7.
5. **Профили «моих задач».** Нужно ли хранить часто используемые связки «задача → модель» для быстрых рекомендаций, или достаточно разовых запросов?
6. **Автообновление.** Нужен ли cron для регулярного обновления снапшота, или обновляем вручную по запросу?
7. **Кто ведёт spotlight.** Список «нашумевших» моделей — курировать вручную (рекомендуется) или формировать автоматически по дате релиза/цене?
